# Java service with a CASA page and Kafka

A team's starting point for a service on the DWP PIP technology stack, with none
of PIP's domain in it. A repository made from this template deploys one GOV.UK
CASA page. A person types a message and presses Send; a Java API publishes it to
Kafka as an Avro record, consumes it again, and the page shows the message's
reference and, once the record has been consumed, `RECEIVED`.

That one round trip uses every part of the stack:

| Part | What it is |
| --- | --- |
| Frontend | [`@dwp/govuk-casa`](https://github.com/dwp/govuk-casa) 10.4.0 on Express 5 and Node 22, Nunjucks views, tested with `node --test` and supertest, linted with ESLint 9 |
| API | Java 25, Spring Boot 4.1.1, Spring Cloud 2025.1.3, Spring Cloud Stream with the Kafka binder, compiled with every warning an error |
| Records | Avro 1.12.2, Java classes generated by `avro-maven-plugin`, written and read by a converter of its own with no schema registry |
| Contract | Spring Cloud Contract 5.0.3 verifier, one contract for `POST /api/messages` |
| Kafka | The environment's Amazon MSK cluster, signed in to with IAM through `aws-msk-iam-auth` 2.3.8 |
| Runtime | ECS Fargate behind an ALB that only CloudFront can reach, HTTPS on CloudFront |

It is the same delivery pipeline as the other golden paths (see
[../DELIVERY-PIPELINE.md](../DELIVERY-PIPELINE.md)): a pull request gets its own
preview of the whole stack, merging deploys `develop`, and a `v*` tag deploys
production. Creating a repository from it also creates one Wayfinder service
account per environment, the `preview`, `develop` and `production` GitHub
environments, and the variables the workflows read, so nobody has to make an
account, a federated credential or a role binding by hand.

## What it needs first

The stack builds no VPC and no Kafka cluster. It finds them by tag in the AWS
account and region it deploys into, and its first deploy fails until both exist:

| Resource | Tags it must carry |
| --- | --- |
| VPC, exactly one per account and region for the environment | `Environment=<environment>`, `ManagedBy=Wayfinder` |
| Its subnets | `Environment=<environment>`, `Tier=public` or `Tier=private` |
| MSK cluster | `Environment=<environment>`, `KafkaCluster=<kafkaCluster input>` (default `default`) |

`<environment>` is the Wayfinder environment name, such as `dev`.

- The `onboard-aws` workflow in the Wayfinder repository
  (`examples/workflows/onboard-aws`) creates a VPC tagged this way when it is run
  with `createVpc`.
- The [`aws-msk-kafka`](../aws-msk-kafka) template in this repository creates an
  MSK cluster tagged this way, with a security group that admits the whole VPC on
  port 9098. So this stack adds no security group rule to reach Kafka.

The ECS tasks run in the VPC's public subnets with a public IP, because a VPC
from `createVpc` has no NAT gateway and the tasks must reach ECR to pull their
images. The generated README says which two lines to change for private
subnets.

## What a repository from it deploys

Eight components, deployed in this order:

```
network ───► platform ───► web ─────────────┐
kafka ──────────────────┐                   ▼
pushimages ─────────────┴──► api ───► frontend ───► smoke
```

`network` and `kafka` find the VPC and the MSK cluster and create nothing.
`platform` is the ECS cluster, the load balancer and the security groups in that
VPC; `web` is the CloudFront distribution; `api` and `frontend` are the two ECS
services. `pushimages` builds and pushes whichever of the two images is missing
from ECR for this `RELEASE`, and `smoke` runs `make smoke` against the CloudFront
URL: both health checks, the page renders, and a message POSTed to the API reads
back `RECEIVED` within about 90 seconds. A deploy whose messages never make it
through Kafka fails there.

`api` is granted `produce-consume` on `kafka` in `Wayfinder.yaml`, and Wayfinder
writes that grant into its task role: connect to the cluster, create, write and
read topics, and join consumer groups. Each instance gets a topic and a consumer
group of its own, named after the stack and the instance, so previews sharing one
cluster never read each other's messages.

Every plan is referenced as `file:plans/...` and ships in the repository. The
two discovery plans are the shared ones every workload uses to find the
platform's network and Kafka; `aws-ecs-platform` takes the VPC and public subnets
it builds in as inputs.

An instance costs about $0.09 an hour in `eu-west-2` before traffic: the load
balancer, two small Fargate tasks and four public IPv4 addresses. The VPC and the
MSK cluster belong to the environment.

Locally, `make up` runs a single-node Kafka broker, both apps and an nginx proxy
standing in for the load balancer on http://localhost:8000, and
`make smoke URL=http://localhost:8000` runs the same check a deploy does.

| File | What it is |
| --- | --- |
| `wayfinder-template.yaml` | The template: its inputs, the service accounts and GitHub variables scaffolding creates, and which files are copied raw. |
| `RepoTemplate-java-casa-kafka-service.yaml` | Registers the template with Wayfinder. |
| `skeleton/` | Everything written into the generated repository. |

See [../ANATOMY.md](../ANATOMY.md) for which of those two YAML files does what.
