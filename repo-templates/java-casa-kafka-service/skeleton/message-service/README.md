# message-service

Accepts a message over HTTP, publishes it to Kafka as an Avro `MessageSubmitted`
record, and reads the record back to mark the message received. Java 25, Spring
Boot 4.1, Spring Cloud Stream with the Kafka binder.

## API

| Request | Response |
| --- | --- |
| `POST /api/messages` `{"message": "..."}` | `201 {"reference":"MSG-7K2M9QX4","status":"SUBMITTED"}`, or `400` naming the field that is wrong |
| `GET /api/messages/{reference}` | `200 {"reference", "message", "status", "submittedAt", "receivedAt"}`, or `404` |
| `GET /api/healthz` | `{"status":"ok","release":"<release>"}` |
| `GET /actuator/health` | Spring Boot health, including the Kafka binder |

```sh
curl -s -XPOST localhost:8080/api/messages -H 'Content-Type: application/json' \
  -d '{"message": "Hello, Kafka"}'
```

A message is `SUBMITTED` once it is accepted and `RECEIVED` once this service has
read its record back off the topic. A message is 1 to 500 characters once
surrounding spaces are dropped. Messages are held in memory, so a restart forgets
them.

## Records

Every message is sent to the `messages.message-submitted` topic (`messages.topic`)
as plain Avro binary with content type `application/avro`. The schema is
`src/main/avro/MessageSubmitted.avsc`; the build generates the Java class from it.
`AvroMessageConverter` checks each record against its schema before writing it
and refuses to send one that does not match, such as one with no reference. There
is no schema registry: both sides use the generated class.

## Build and test

Needs JDK 25 and Maven 3.9.

```sh
mvn -B test                      # message flow, converter and contract tests
mvn -B package -Drelease=v1.2.3  # target/message-service.jar
docker build --build-arg RELEASE=v1.2.3 -t message-service .
```

The contract test is generated by Spring Cloud Contract from
`src/test/resources/contracts` and runs against the whole application, with Spring
Cloud Stream's in-memory test binder in place of Kafka.

## On AWS

Run with `SPRING_PROFILES_ACTIVE=aws` and `KAFKA_BOOTSTRAP_SERVERS` set to the MSK
IAM bootstrap brokers. The `aws` profile signs in to MSK with IAM as the ECS task
role, so the task role needs permission to connect, create and describe the topic,
write and read it, and join its consumer group. The stack grants exactly that
through the `produce-consume` policy on its `kafka` component.

The `aws` profile also names the topic `<APP_NAME>.<APP_ENV>.message-submitted` and
the consumer group `<APP_NAME>.<APP_ENV>.message-service`. The ECS task sets
`APP_NAME` to the stack and `APP_ENV` to the instance, so every instance sharing
one MSK cluster reads and writes only its own messages.

## Why `.mvn/maven.config` switches Maven's HTTP transport

The Spring Cloud Contract plugin brings its own Apache HttpClient. Any artifact
Maven downloads after that plugin has run (surefire's JUnit provider on a first
build, for instance) fails with `BasicAuthCache cannot be cast to AuthCache`. The
wagon transport does not share those classes, so a build with an empty Maven
cache, such as a fresh CI runner, works.
